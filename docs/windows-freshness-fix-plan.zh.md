# Windows 文件系统新鲜度修复计划

[English](windows-freshness-fix-plan.md) | 中文

状态：用户已通过本地修复审批问题批准。本计划仅修改隔离的 `turn-step-state` worktree，不授权提交、推送、安装、重建或重启运行中的 harness、修改 Windows 策略或部署。

## 问题与证据

当前 `FileSystem.stat()` 返回元数据版本，`readText()` 和 `streamText()` 返回内容，但不提供绑定到这些字节的版本。文本读取工具、图像读取工具和字符串替换编辑器的 view 记录读取前的版本。受测 Windows 文件系统上的普通读取可能更新访问时间和 ctime，立即使观察失效。

相关契约：

- `packages/fs/fs/src/index.ts`：stat/lstat 只返回元数据；目录列表不得读取内容；后端负责文本解码。
- `packages/fs/fs-local/src/index.ts`：修改守卫在逐目标锁内、匹配前执行，目前比较元数据字符串。
- `packages/fs/tool-fs/src/read.ts`、`read-image.ts` 和 `packages/fs/tool-str-replace-editor/src/index.ts`：成功读取记录读取前版本。
- `packages/fs/fs-local/tests/filesystem.spec.ts`：现有同大小、恢复 mtime 测试使用原子替换文件的 `fs.writeText`，未隔离保留文件标识的原地覆盖。

此前调查已有可重现失败。制定本计划时尚未修改新的实现或测试代码。

## 最小完整改动

增加可选后端版本化读取能力，保持现有元数据 API 和普通非观察读取兼容：

1. 版本化文本流在完整原始字节哈希与文本验证成功后，以最终完成值返回不透明 `FsVersion`。消费者捕获完成值，现有窗口构建器仍消费全流。不完整或取消的流不得返回最终令牌。
2. 有界原始字节读取同时返回字节和版本，供图像读取使用。
3. 本地后端每次读取使用单个文件句柄，解码前增量计算完整 SHA-256，并检查文件标识。句柄/路径替换或可检测的不稳定读取必须拒绝。令牌绑定交付字节，而非未经核验的读取后元数据。
4. 读取工具优先使用新能力，仅在成功完成后发布观察。不支持的后端保留元数据令牌行为，不新增内容版本保证。
5. 本地修改在既有锁内识别内容令牌，匹配或替换前验证标识和内容。尽可能复用编辑所需字节，否则增量哈希。旧 stat 令牌保持严格元数据比较，非法令牌拒绝。
6. 本地 write/edit 结果返回绑定已写字节的令牌，避免后续编辑退回脆弱元数据观察。发布后的不确定性不得授权未观察到的不同字节。

令牌在后端之外保持不透明。必须使用完整 SHA-256，不得截断或采用非加密哈希。不得记录摘要或放入模型可见错误。缓存不得将旧令牌重新绑定到新内容。

内容新鲜度与访问时间记账有意分离；这不是完整元数据审计。权限检查、沙箱边界、DACL 保留和原子发布机制不变。

## 阶段与依赖

### 1. 契约与确定性红灯测试

先定义能力和令牌规则，通过现有 Vitest runner 添加并观察失败测试，再实现。使用仅限 fixture 的竞态钩子，不使用 sleep 或机器级时间戳修改。

必要测试：

- 读取后的访问时间/ctime 漂移不阻止未变字节的守卫编辑。
- 同长度、同标识、恢复 mtime 的不同内容原地覆盖被拒绝。
- 读取字节后、完成前的修改不能借助读取后时间戳获得授权。
- 旧句柄打开时路径被替换会被拒绝。
- 独立观察不能互相重绑定；B 读取新内容后，A 的旧观察仍失效。
- 同会话并发守卫修改只有一个胜者。
- 编辑未匹配或匹配歧义不因读取更新时间戳而使内容观察失效。
- 旧元数据守卫仍严格拒绝失效版本。

### 2. 本地实现与消费者集成

观察预期失败后实现能力，更新全部三个观察读取入口。保持观察策略词汇和 actor/session 隔离；沙箱修改检查仍在任何守卫修改 I/O 前执行。

覆盖 BOM/CRLF 原始字节、窗口读取后的全文件守卫、二进制/图像、非法 UTF-8、空文件、缺失及重建、取消、部分消费、文件增长和写后编辑。验证内容版本稳定性，不宣称 Windows 元数据读取后不变。

### 3. 验证

使用现有命令并保留完整汇总和退出码：

- `vitest.CMD run packages/fs --maxWorkers=1 --reporter=default`
- Mock E2B 文件系统测试，不连接云沙箱。
- 先前通过的 core agent/session、subprocess、PowerShell 工具选择（基线 42 文件、819 测试）。
- 使用已安装 TypeScript 构建受影响项目。
- 有界 Windows 集成重复仅为补充证据，不能替代确定性竞态测试。

独立完整运行结束前不宣称全仓通过；未在 Linux 执行则不宣称 Linux 通过。

## 验收标准

- 确定性测试先红后绿。
- 访问时间/ctime 变化下，未变内容的读取后写入/编辑成功。
- 同大小恢复 mtime、标识替换、旧观察和确定性并发写入在匹配/发布前被拒绝。
- stat、lstat、目录列表不隐藏新增全文件内容 I/O。
- 流内存有界，取消和增长边界限制守卫扫描。
- 部分读取不能授予全文件观察。
- 沙箱/权限、秘密过滤、远程后端行为不回退。
- 全部观察读取入口和修改结果使用适当版本契约。

## 风险与明确限制

内容守卫替换需要 O(文件大小) 扫描，除非编辑已需要这些字节。应测量并记录成本，不得以仅元数据捷径移除扫描。

逐目标锁仅串行化 DSH 自身修改。摘要和标识检查不是对任意外部写入的内核级原子比较替换；最终验证之后仍有发布竞态窗口。应缩小窗口并测试选定交错，不承诺文件系统事务，也不新增通用重试引擎来掩盖它。

不得从旧令牌移除 ctime、认可未验证读取后版本或禁用 Windows 访问时间。默认不使用原生 `SetFileTime` 抑制：它需要 `FILE_WRITE_ATTRIBUTES`，扩大读取所需权限。来源：https://learn.microsoft.com/windows/win32/api/fileapi/nf-fileapi-setfiletime

独立设计评审仅供参考；未采纳截断/非加密哈希、未完成流版本或原生时间戳抑制建议。
